# Appendix F. Benchmark Methodology

性能数字的可信度取决于测量方法。同一个 kernel，不同的计时方式能差出 2 倍。

## F.1 计时

**用 CUDA event，不要用墙钟。** `cudaEventRecord` 在 stream 上打点，测的是 GPU 侧的时间，不受 CPU 调度抖动影响：

```cpp
cudaEvent_t start, stop;
cudaEventCreate(&start);
cudaEventCreate(&stop);
cudaEventRecord(start);
kernel<<<grid, block>>>(...);
cudaEventRecord(stop);
cudaEventSynchronize(stop);
float ms;
cudaEventElapsedTime(&ms, start, stop);
```

几点注意：

- **预热**：第一次执行包含上下文初始化、JIT 编译、缓存冷启动。至少预热 10 次，取后面的稳定值；
- **同步位置**：event 只测量两个 event 之间的 GPU 工作。如果中间有隐式同步，测到的是“被阻塞的时间”；
- **多次迭代**：单次测量噪声大，跑 100 次取中位数和 P90；
- **锁频**：GPU 会动态调频，跑得越久越可能降频。用 `nvidia-smi -lgc` 锁定频率，否则前后对比没有意义。

## F.2 统计量

| 指标 | 用途 | 注意 |
| --- | --- | --- |
| 均值 | 吞吐 | 受长尾影响大 |
| 中位数 | 典型延迟 | 对离群值稳健 |
| P90 / P99 | 尾延迟 | 服务 SLO 的核心指标 |
| 标准差 | 稳定性 | 要配合样本量看 |
| 置信区间 | 结论的可靠性 | 样本少时必须有 |

报告延迟时至少要给 P50 和 P99；只报均值等于隐藏了最差的那部分用户体验。

## F.3 常见陷阱

- **比较不同的工作量**：A 配置的吞吐高，可能是因为它的输出更短。要比单位 token 的成本；
- **忽略预热和编译**：`torch.compile` 的首次运行包含几十秒编译，把它算进吞吐会严重低估；
- **测量包含了 Python 开销**：端到端测量和 kernel 测量的差值，本身就是有价值的信息，但要分清；
- **只测单请求**：单请求的延迟和批量服务的延迟是两回事，batch 会同时改变两者；
- **缓存效应**：重复跑同一批数据，权重可能已经在 L2 里，真实流量不会这么幸运。

## F.4 实验模板

一个可复现的性能实验应该记录：

```text
硬件：GPU 型号、数量、互联方式、驱动/CUDA 版本
软件：框架版本、编译选项、kernel 配置
模型：参数量、精度、序列长度、batch
工作负载：输入/输出长度分布、并发数
指标：吞吐、TTFT、TPOT 的 P50/P90/P99
方法：预热次数、迭代次数、计时方式
```

缺少任何一项，别人都无法复现你的数字。尤其是“序列长度”和“并发数”——很多对比的差异来自这两个参数，而不是被优化的技术本身。

## F.5 消融实验

判断一个优化是否有效，要做消融：保持其他条件不变，只改一项。

```
基线           → 3,200 tok/s
+ 融合 kernel  → 3,450 tok/s  (+7.8%)
+ CUDA Graph   → 3,900 tok/s  (+13.0%)
+ 两者         → 4,050 tok/s  (+3.8% 额外)
```

最后一行很重要：两个优化可能互相重叠（比如 CUDA Graph 已经消除了部分 launch 开销，融合 kernel 的收益就被削弱）。单独测每一项会高估总收益。

## F.6 与 SLO 对齐

性能数字最终要落到业务指标上。压测时至少覆盖三个点：

- **容量点**：P99 刚好满足 SLO 的并发；
- **拐点**：延迟开始非线性上升的并发；
- **崩溃点**：开始出现超时或 OOM 的并发。

容量规划取容量点的 70%，留出突发和故障转移的余量。
